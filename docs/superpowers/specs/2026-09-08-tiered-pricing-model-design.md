# 0. הבעיה

המודל הקיים הוא מחיר אחד קבוע לכל ספק — שורת `PAYPLUS` (ישראל) ושורת
`STRIPE` (כל שאר העולם, מחיר אחד לכל 26+ מדינות תיירות מרפא). אין מדרגות,
אין תקרת בקשות, אין Featured, אין מדד תגובה. הטריאל הוא קבוע-קלנדרי
(`trialDays`) שנספר מרגע האישור, לא מרגע שהמרפאה קיבלה ערך אמיתי.

מסמך הניתוח (`dentalcompare-pricing.html`) מציע: 4 מדרגות (רשומה חינמית,
Basic, Pro, Featured) × 2 שווקי מחיר (ישראל, תיירות מרפא — תואם את הפיצול
הקיים PAYPLUS/STRIPE), תקרת בקשות חודשית לכל מדרגה, טריאל מבוסס-תוצאה
(5 בקשות מאומתות במקום 60 יום), SLA תגובה שמוריד מרפאה שלא עונה מהסינון,
Featured עם מלאי מוגבל, ותקופת Founding עם הנחה אוטומטית ל-50 המצטרפות
הראשונות.

# 1. החלטות סגורות

התקבלו בליבון מול אדן ב-2026-09-08.

## 1.1 הטריאל מוחלף לגמרי — לא מתווסף

הטריאל הקיים (`trialDays`, `trialEndsAt`, `dueTrialWarning` הקלנדריים
ב-`src/lib/subscription.ts`) **מפסיק להיות מנגנון ה"מתי הטריאל נגמר"**.
במקומו: מרפאה TRIALING עוברת לחיוב כשהיא מצטברת `trialRequestCap` בקשות
מאומתות (ברירת מחדל 5). מנגנון החידוש הקלנדרי (`nextPeriodEnd`,
`isDueForRenewal`, `isWithinGrace`, ה-cron היומי) **לא זז** — הוא ממשיך
לרוץ *אחרי* ההמרה, בדיוק כמו היום, על בסיס `plan` (MONTHLY/YEARLY).

## 1.2 "בקשה מאומתת" = `RequestDentist.sentAt` נקבע, ומתבטלת ב-dispute

בקשה נספרת (גם לטריאל וגם לתקרה החודשית) ברגע ש-`sentAt` נקבע — זה כבר
הרגע הקיים במערכת שבו תוכנית טיפול וצילום *בפועל* יצאו למרפאה. אם
`disputedAt` מסומן על אותה שורה אחר כך, היא יורדת מהספירה (גם ממונה
הטריאל המצטבר וגם מהמונה החודשי) — סימטרי לפיצוי הקיים של ימי מנוי על
ליד שגוי.

## 1.3 תקרת הבקשות היא **חודשית**, נפרדת מסך הטריאל המצטבר

`ClinicSubscription.verifiedRequestCount` (מצטבר-לכל-החיים, לצורך המרת
טריאל בלבד) ו-`MonthlyRequestUsage` (מתאפס כל חודש קלנדרי, לצורך תקרת
המדרגה) הם שני מונים נפרדים שגדלים/קטנים באותו אירוע.

## 1.4 מדרגת "רשומה" (FREE) מקבלת שורת `ClinicSubscription` מפורשת

`plan=FREE` הוא שורה אמיתית, לא "אין שורה" — כדי לא לפתוח מקום נוסף
שמרפאה נעלמת ממנו בלי שגיאה (אותה משפחת באג כמו `visibleSubscriptionFilter`
ושער הרישיון).

## 1.5 SLA תגובה: 48 שעות, 2 רצופות בלי מענה = ירידה מהסינון

חל על כל המדרגות כולל Featured. מתאפס כש-`Quote` מוגש.

## 1.6 Featured: מלאי קשיח — 3 לכל `(city, specialty)`, רוטציה שווה בתוך המלאי

לא "בלי תקרה, רק רוטציה" (כמו בגרסת ה-Downloads) — מלאי אמיתי עם הודעת
"מלא, הצטרפו לרשימת המתנה" כשנתפס.

## 1.7 Founding 50 — מונה אוטומטי בקוד, לא פעולה ידנית

51 ואילך משלמות מחיר מלא אוטומטית, בלי שאדן צריך לזכור להחליף מסך.

## 1.8 תקרות הבקשות לכל מדרגה ניתנות לעריכה באדמין, כמו המחיר

לא קבועים בקוד — אותו דפוס בדיוק כמו `updatePricing` הקיים.

## 1.9 מלאי ה-Featured (3 לכל צירוף) הוא קבוע מערכתי, לא נבדק אם ניתן לעריכה

לא עלה כשאלה פתוחה בליבון; אם אדן ירצה זאת ניתן לעריכה — תוספת קטנה
בהמשך, לא חוסמת את התכנון הנוכחי.

# 2. המודל

```prisma
enum SubscriptionTier {
  FREE
  BASIC
  PRO
  FEATURED
}

model SubscriptionPricing {
  provider          SubscriptionProvider
  tier              SubscriptionTier
  currency          String   // בירושה מהספק, לא ניתן לעריכה — כמו היום
  monthlyPriceMinor Int      // FREE נעול ל-0 בוולידציה
  yearlyPriceMinor  Int      // FREE נעול ל-0 בוולידציה
  monthlyRequestCap Int?     // null = ללא הגבלה (FEATURED)
  trialRequestCap   Int      // מחליף את trialDays; משמעותי רק בטריאל שמוביל למדרגה זו
  updatedAt         DateTime @updatedAt
  updatedBy         String?

  @@id([provider, tier])
}

model ClinicSubscription {
  // ...שדות קיימים ללא שינוי...
  tier                   SubscriptionTier @default(FREE)
  // נצרב בהרשמה, כמו priceMinor/currency/trialDays היום
  trialRequestCap        Int?
  // מצטבר-לכל-החיים, לצורך המרת טריאל בלבד (ר' 1.3)
  verifiedRequestCount    Int              @default(0)
  isFounding              Boolean          @default(false)
  foundingDiscountExpiresAt DateTime?
}

model MonthlyRequestUsage {
  dentistId String
  dentist   Dentist  @relation(fields: [dentistId], references: [id], onDelete: Cascade)
  yearMonth String   // "2026-09", מפתח טבעי לאיפוס חודשי בלי cron נפרד
  count     Int      @default(0)

  @@id([dentistId, yearMonth])
}

model FeaturedSlot {
  city       String
  specialty  String
  dentistId  String
  dentist    Dentist  @relation(fields: [dentistId], references: [id], onDelete: Cascade)
  claimedAt  DateTime @default(now())

  @@unique([city, specialty, dentistId])
  @@index([city, specialty])
}
```

מיגרציה עם שורות זרע — 8 שילובי provider×tier. `PAYPLUS`/`BASIC` ו-
`STRIPE`/`BASIC` יורשים את הערכים החיים היום (₪199/₪1,990 ו-שווה-ערך
בינלאומי), לא את המחיר השטוח הישן.

**`trialDays` נשאר על `SubscriptionPricing` הישן?** לא — מוחלף ב-
`trialRequestCap` על אותה שורה (מפתח מורכב חדש ממילא מחייב מיגרציה מלאה
של הטבלה, אין טעם לשמור שדה מת לצידו).

# 3. אכיפת תקרות + כלל הרצפה

`publicDentistWhere()` (`src/lib/dentist-public.ts`) נשאר הגייט הבסיסי
(`isActive`, רישיון, `visibleSubscriptionFilter`) — **לא** מקבל את תנאי
התקרה, כי התקרה תלוית-הקשר (עיר×התמחות) ולא ניתנת לביטוי כ-`where` שטוח.

פונקציה חדשה, `filterByRequestCap(dentists, city, specialty)`, רצה
**אחרי** השאילתה הבסיסית במסלולים שמציגים רשימה לפי עיר/התמחות (מסך
הסינון של המטופל):

1. הסר מרפאות שהגיעו לתקרה החודשית שלהן (`MonthlyRequestUsage` מול
   `monthlyRequestCap` הנצרב על ה-`ClinicSubscription`).
2. אם התוצאה לאותו `(city, specialty)` ירדה מתחת ל-5 — החזר בהדרגה
   מרפאות שהוסרו (ממוינות לפי ותק/דירוג) עד לרצפה.

מסלולים שלא מפולחים לפי עיר/התמחות (מונה דף הבית, למשל) ממשיכים להשתמש
ב-`publicDentistWhere()` בלבד — התקרה לא רלוונטית שם, זה סך-הכול, לא
רשימת בחירה.

**מוצא ל-open questions בתוכנית הביצוע**: בדיוק אילו מסלולים בקוד היום
מפולחים לפי עיר/התמחות (ומכאן צריכים את הפונקציה הדו-שלבית) לעומת אלה
שמסתפקים בגייט הבסיסי — צריך מיפוי מדויק של `dentist-public.ts` הקיים
וקוראיו לפני כתיבת קוד.

# 4. SLA תגובה

`Dentist.slaBreachedAt DateTime?` — עמודה חדשה.

Cron יומי חדש (מצטרף לקרון הקיים) סורק `RequestDentist` עם `sentAt` לפני
יותר מ-48 שעות ובלי `Quote` מקושר; אם נמצאות 2 רצופות (לפי `sentAt`) בלי
מענה — מסמן `slaBreachedAt = now()`. מתאפס (`null`) כש-`Quote` הבא מוגש.

`publicDentistWhere()` מקבל תוספת: `slaBreachedAt: null` — זה **כן**
where-clause שטוח, לא תלוי-הקשר, אז נכנס לגייט הבסיסי.

---

# 5. Featured — מלאי ורוטציה

הרשמה/שדרוג ל-Featured בודקת `COUNT(*) WHERE city=X AND specialty=Y` מול
`FeaturedSlot` לפני יצירת שורה. 3 ומעלה → נדחה, מוצג מסך "המלאי מלא,
הצטרפו לרשימת המתנה" (רשימת ההמתנה עצמה — טווח פתוח לתוכנית הביצוע: יכולה
להיות רשימת מייל פשוטה בשלב ראשון, לא תור אוטומטי).

בדף התוצאות, מרפאות עם `FeaturedSlot` פעיל לאותו `(city, specialty)`
מוצגות בבלוק "מומלצות" בראש הרשימה, בסדר שמתחלף בכל רינדור (לא ממוין
קבוע) — רוטציה שווה בתוך המלאי התפוס, לא תחליף למלאי עצמו.

---

# 6. Founding 50

ב-`registerClinic`/`approveClinic` (המקום הנוכחי שבו `priceMinor` נצרב):
`COUNT(*) WHERE isFounding = true` — אם < 50, `isFounding = true` ו-
`priceMinor` נחתך ב-50% לפני הצריבה. שורה 51 ואילך: `isFounding = false`,
מחיר מלא, בלי צורך בהתערבות ידנית.

ברגע שהטריאל ממיר לחיוב בפועל (סעיף הבא) — אם `isFounding`,
`foundingDiscountExpiresAt = now() + 12 חודשים`. ה-cron הקיים של חידוש
(`renew-subscriptions`) צריך לבדוק את זה: אחרי `foundingDiscountExpiresAt`,
`priceMinor` חוזר למחיר המלא של המדרגה (מ-`SubscriptionPricing` הנוכחי,
לא נעול עוד).

# 7. המרת טריאל מבוסס-תוצאה

כשכל אירוע שמעדכן `verifiedRequestCount` מעלה אותו ל-`>= trialRequestCap`
הנצרב, מופעל **מיידית** (לא ממתין לקרון היומי) אותו נתיב "נסה חיוב ראשון"
שקיים כבר ב-`renew-subscriptions` — כדי שהמרה תרגיש מיידית למרפאה, לא
תלוית-קרון. הקרון היומי נשאר כרשת ביטחון (מרפאה שהגיעה לסף אך הניסיון
הראשון נכשל/PayPlus לא היה מוגדר) — לא נבנה נתיב הפעלה שני, אלא קורא
לאותה פונקציה.

# 8. מסך האדמין

`/[locale]/admin/subscriptions` — הפאנל הקיים (2 שורות: PayPlus/Stripe)
הופך לרשת 8 שורות (2 ספקים × 4 מדרגות). לכל שורה: מחיר חודשי, מחיר שנתי,
תקרת בקשות חודשית (ריק = ללא הגבלה), סף טריאל, מי/מתי עדכן לאחרונה. שדה
FREE: מחיר נעול ל-0 בוולידציית `updatePricing` (לא רק מוסכמה ב-UI).

פאנל קריאה-בלבד נוסף: "Founding: X/50 נתפסו" — ללא עריכה.

# 9. מחוץ להיקף

- ייעוץ משפטי בפועל על הגבלת תשלום-בעד-הפניה — תנאי לפני הטמעה, לא חלק
  מהתוכנית הזו.
- רשימת המתנה אוטומטית ל-Featured (תור, עדיפות) — בשלב ראשון מייל/רשימה
  ידנית מספיקה.
- הגירה/grandfathering של מנויים קיימים — לא רלוונטי, **אין עדיין אף
  מרפאה אמיתית בפרודקשן**.
- שינוי מטבע לספק קיים, גרסאות/היסטוריית מחיר — כמו בתת-פרויקט א', עדיין
  מחוץ להיקף.
- עריכת מלאי ה-Featured (3) באדמין — אפשרי בעתיד, לא כלול כאן (ר' 1.9).

# 10. חלוקה מוצעת (לתוכנית ביצוע)

1. מיגרציה: `SubscriptionTier`, `SubscriptionPricing` עם מפתח מורכב
   ושורות זרע, `ClinicSubscription` שדות חדשים, `MonthlyRequestUsage`,
   `FeaturedSlot`, `Dentist.slaBreachedAt`.
2. מונה בקשות: hook על `sentAt`/`disputedAt` שמעדכן `verifiedRequestCount`
   ו-`MonthlyRequestUsage` יחד, עם בדיקות.
3. המרת טריאל מבוסס-תוצאה — קריאה מיידית לנתיב החיוב הקיים + עדכון הקרון
   כרשת ביטחון.
4. `filterByRequestCap` + כלל הרצפה, אחרי מיפוי מדויק של קוראי
   `publicDentistWhere()` (ר' סעיף 3).
5. SLA תגובה — cron + עדכון `publicDentistWhere()`.
6. Featured — `FeaturedSlot`, בדיקת מלאי בהרשמה, תצוגת רוטציה.
7. Founding 50 — מונה + חיתוך מחיר + פקיעה אחרי 12 חודש בקרון החידוש.
8. מסך האדמין: רשת 8 השורות + פאנל Founding.
9. אימות סופי: מעבר ידני מלא (רישום → הגעה לתקרה → ירידה מהסינון →
   תחילת חודש → חזרה; רישום → 5 בקשות → חיוב מיידי; SLA → ירידה →
   Quote → חזרה; Featured מלא → הודעת מלאי).

# 11. פתוח

- **מיפוי מדויק של קוראי `publicDentistWhere()`** — אילו זקוקים לגרסה
  הדו-שלבית (עם תקרה+רצפה) ואילו לגייט הבסיסי בלבד. נדרש לפני משימה 4.
- **ייעוץ משפטי** על הגבלת תשלום-בעד-הפניה — לפני שמתחילים לממש בפועל
  (לא לפני תכנון/כתיבת תוכנית).
- מנגנון רשימת ההמתנה ל-Featured — טווח מדויק, מחוץ להיקף לעת עתה.

## הוספות מהסקירה הסופית של תת-פרויקט 1 (schema + admin), 2026-09-09

תת-פרויקט 1 (`docs/superpowers/plans/2026-09-08-tiered-pricing-schema-and-admin.md`)
נחת. הסקירה הסופית שלו (opus) העלתה שתי נקודות מבניות שצריכות
להפוך לאילוצים מפורשים בתוכנית הבאה (תקרות + כלל הרצפה), לא רק
הערות:

- **`ClinicSubscription` צריך שדות "תמונת מצב" ל-`monthlyRequestCap`
  ו-`trialRequestCap`, לא רק `tier`.** כל שדה שכן שלה היום
  (`priceMinor`, `currency`, `trialDays`) נצרב ברגע היצירה בכוונה —
  בדיוק כדי שעריכת מחיר באדמין לא תשנה רטרואקטיבית מה שמרפאה קיימת
  כבר הסכימה לו. `tier` (שנוסף בתת-פרויקט 1) שובר את התבנית הזו: הוא
  מצביע חי על `SubscriptionPricing`, כך שעריכת התקרה של BASIC באדמין
  תשנה בפועל את התקרה של כל מרפאה קיימת ב-BASIC. סעיף 2/3 של המסמך
  הזה כבר מניחים "תמונת מצב" — התוכנית הבאה חייבת להוסיף את שני
  השדות בפועל ל-`ClinicSubscription`, ולא להסתפק ב-`tier` כמקור
  היחיד לזכאות.
- **`ClinicSubscription.tier` נשאר `@default(BASIC)` קבוע.** זה נכון
  היסטורית (כל שורה קיימת היא באמת "Basic"), אבל בניגוד ל-
  `provider @default(PAYPLUS)` (ששני הערכים בו הם בתשלום, אין כיוון
  "שגוי") — כאן יש כיוון מועדף מדי: נתיב כתיבה עתידי ששוכח `tier`
  יעניק בשקט זכאות של מדרגה **בתשלום**. בתוכנית שמכניסה הרשמה חינמית
  אמיתית בפועל (סעיף 1.4 — "רשומה" מקבלת שורת `ClinicSubscription`
  מפורשת) — יש להוריד את ברירת המחדל הזו, באותו דפוס בדיוק שכבר קיים
  ל-`priceMinor`/`currency`/`trialDays`: להוסיף עם ברירת מחדל זמנית,
  לבצע backfill, ואז `DROP DEFAULT` כדי שכתיבה עתידית שלא מציינת
  `tier` תיכשל בקול רם.
